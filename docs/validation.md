# 历史验证记录

日期：2026-09-19。环境：MacBook Pro M4 Pro、48 GB 内存、macOS 27.0、Rust 1.96.0。
此表区分软件契约、实物通信和尚未验证的定位 / 性能；不以单个平台通过代替其他平台。

最新高频修复与实测见 [OSC 调度与 BLE 通知分析](measurements/2026-09-19-osc-timing.md)：
macOS USB 200 Hz 档已接近 198 Hz OSC 输出，Windows 模拟器达到约 200 Hz；BLE 200 Hz 档仍约 25 次通知／秒。
下文的 10 Hz 实机数据保留为初始通信验收，不代表设备或桥接程序的最高速率。

后续 [macOS BLE 探索](measurements/2026-09-19-ble-exploration.md) 确认设备版本号 13115、50–200 Hz 打包策略，
以及带时间戳的 200 Hz 档原生四元数主动上报。改变报文内容与有限并行读取仍未突破约 25 次通知/秒；新格式现已接入正式 bridge；最新[时间戳链路验证](measurements/2026-09-19-timestamp-pipeline.md)单独记录。

## 初版软件检查（最新时间戳增量见上文链接）

- Release 核心契约测试：9 项通过，覆盖数据解析、7 组姿态向量、安装转换、OSC 编码 / 限速、失联恢复、生命周期和 BLE 可选配置。
- OSC 调度回归：3 项通过，覆盖定时抖动下的 200 Hz 节奏、最新值合并、无重复／补帧、陈旧数据与新会话。
- Unix 伪串口测试：3 项通过，覆盖真实异步串口收发与 OSC、拆包、失联恢复、EOF、配置回读和不隐式保存，
  以及四元数请求的单请求限制、超时重试与停止。该测试发现并促成移除阻塞式串口 drain。
- Release CLI → 本机 UDP：Euler 和四元数消息均由独立 Python 解码器验证通过。
- 真实 C 调用程序：动态库加载 / 链接、版本、结构大小、缓冲不足、无数据、重复轮询、停止和重启通过。
- 动态库迁移：使用 `@rpath/libposebridge_capi.dylib`，复制到独立临时目录后编译和运行 C 调用程序通过，无本机编译目录依赖。
- macOS 动态库最初遇到 strip 后 Mach-O 字符串表对齐错误；关闭额外 strip 后 C 链接与运行通过。
- 格式与 Clippy：`cargo fmt --all --check` 与 Release 全目标 Clippy（`-D warnings`）通过。

## macOS 实物通信

传感器广播名称为 `WT901BLE68`，商品型号 BWT901BLECL5.0；最初验收时未读取版本，后续已确认设备版本号 13115。
连接使用本机内置蓝牙，未购买专用适配器，也未调用系统常规配对流程。

| 路径 | 本次结果 | 限制 |
|---|---|---|
| BLE 扫描 | 成功发现设备并取得平台 UUID | UUID 属于本机身份，不写入通用配置 |
| BLE 角度通知 | 8 秒诊断窗口中连接后收到 57 份有效角度，主机观察约 9.88 Hz；无丢弃字节、无效姿态或重连 | 包含连接建立时间；保留默认设备回传率，没有执行配置写入 |
| BLE 四元数寄存器读取 | 8 秒诊断窗口中连接后收到 100 份四元数，约 16.17 Hz；无解析错误或重连 | 程序最高请求节奏 50 Hz，实际返回远低于 200 Hz；只发读取寄存器命令 |
| USB Rust 实机 | 115200、8N1；两次独立 4 秒运行的最后状态分别为 37／38 份角度，均约 9.93 Hz；无丢弃字节或无效姿态 | 已验证正常关闭后可再次打开；未执行物理拔插或回传率写入 |
| USB → 本机 OSC | 4 秒窗口收到 40 个四元数数据报，地址、类型及单位范数检查通过 | 使用显式安装基底验证数据流，不代表耳机安装方向或音频定位已验证 |

上述角度与四元数率是各自独立采集窗口的主机观察，不能相加，也不是传感器内部采样率。
BLE 原始角度在连接初期有变化，尚未完成稳定性、安装方向、漂移或磁场校准验收，不据此声称定位精度。

## 尚未验证

- Windows USB 的 50／100 Hz 扫频、Flash 保存持久性和校准结果。200 Hz 时间戳格式的最新实测见上文链路记录，
  该轮观察到主机批量交付，不能据此声称 USB OSC 已达 200 Hz。
- BLE 更短通知打包周期的设备配置／固件支持；未通过推测寄存器、补发旧帧或插值声称解决。
- 最终耳机安装位置的三轴正方向、磁干扰、长期漂移、断电或远离后的真实重连表现。
- 个人 SOFA、GUI 适配和转头到声音变化的整体延迟。MacinRender 原生 OSC v1/v2 已验证，不能代替音频链路验收。

## Windows 本机与 CI

环境：Windows x64（build 26200）、Rust 1.98.0 MSVC、MSVC 14.51、Windows SDK 10.0.26100.0。
本机通过格式检查、Clippy、9 项核心契约测试和 3 项 OSC 调度测试、Release 构建、头文件一致性、CLI → OSC 与真实 C ABI 迁移调用。
Unix 伪串口的三项测试不在 Windows 上运行。

[首次双平台 CI](https://github.com/SakuzyPeng/PoseBridge/actions/runs/35435906366) 的 macOS 和 Windows 任务均通过。
该链接属于先前提交；本次高频修复使用两台本机原生验证，尚未推送触发新的 CI。
首次 Windows CI 暴露了 C smoke 变量 `small` 与 Windows SDK 宏重名的问题，修复为 `undersized_pose` 后通过。
原生库随后改用 `posebridge_capi` 文件名，避免 Windows CLI／动态库的 PDB 输出冲突。
头文件导出在内容相同时保留已有 CRLF 文件，避免仅因换行重写而污染 Windows 工作区。

同一台 `WT901BLE68` 的本机实物结果如下，普通采集保留设备回传配置：

| 路径 | 本次结果 | 限制 |
|---|---|---|
| USB 枚举与读取 | COM3，USB-SERIAL CH340；两次 5 秒运行的最后状态均为 47 份角度，约 9.95 Hz；无解析错误或重连 | 已验证正常关闭后重开，未测试运行中物理拔插 |
| USB → OSC | 4 秒窗口收到 39 个四元数包，地址、类型和单位范数检查通过 | 仅验证数据流，不代表头部安装或音频定位验收 |
| BLE 角度通知 | 8 秒运行中连接后收到 57 份角度，约 9.93 Hz；无解析错误或重连 | 窗口包含连接建立时间 |
| BLE 四元数读取 | 8 秒运行的最后状态为 48 份四元数，约 17.70 Hz；无解析错误或重连 | 独立寄存器请求模式，不是 200 Hz 持续推送 |

这些是主机观察的短时通信结果，不是定位精度、长期稳定性或运动到音频延迟的测量。
