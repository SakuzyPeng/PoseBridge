# macOS BLE 后续探索

日期：2026-09-19。WT901BLE68，macOS Apple Silicon，Release，btleplug 0.11.8。
基础版本 `4b88a9b`；本轮新增独立实验工具，没有改动正式 bridge／C ABI 的采集行为。

## 结论

**本轮没有找到将 BLE 的约 25 次新姿态交付／秒继续提高的方法。**
缩短报文、只输出角度、只输出原生四元数，以及有限并行主动读取，均没有突破该频率。
厂家新版规格书明确注明：**“50Hz~200Hz数据打包传输”**，与实测一致。

同时确认了以前未知的能力：这台设备支持 **200 Hz 档的原生四元数主动上报和设备时间戳**。
批内时间戳每 5 ms 增加，批量到达约 25 Hz；“设备产生新样本”和“主机获得新姿态”是两个不同的频率。

设备 `0x2E/0x2F` 原始值为 `0x333B/0x0000`。
官方 SDK 在 32 位版本字段最高位未置位时直接显示 `0x2E` 的十进制值，因此这里版本号记为 **13115**，
不能套用扩展版本公式写成 `0.51.59`。现场配置是九轴、20 Hz 滤波带宽，未改动融合或滤波参数。

## 厂商资料与报文格式

新版协议用 `0x0E` 选择输出内容；默认值为 `0x61`。本机读回值也为 `0x61`，随后按公开协议临时切换并核验：

| 200 Hz 档输出 | 标志 | 单帧长度 | 实测每通知字节数 | 通知率 |
|---|---:|---:|---:|---:|
| 加速度＋角速度＋角度 | `0x61` | 20 | 160，即 8 帧 | 24.87 Hz |
| 仅角度 | `0x01` | 8 | 64，即 8 帧 | 24.82 Hz |
| 仅原生四元数 | `0x04` | 10 | 80，即 8 帧 | 24.81 Hz |
| 时间戳＋角度 | `0x81` | 16 | 128，即 8 帧 | 24.91 Hz |
| 时间戳＋原生四元数 | `0x84` | 18 | 144，即 8 帧 | 24.88 Hz |
| 时间戳＋角速度＋原生四元数 | `0xA4` | 24 | 192，即 8 帧 | 24.86 Hz |

100 Hz 默认格式是一份通知 4 帧／80 字节，24.87 次/秒；20 Hz 默认格式是一份通知 1 帧／20 字节，19.80 次/秒。
减少 payload 并未减少每批样本数，排除了“默认 20 字节报文太大”这一直接改进方向。

`0x81` 有 1591 个连续设备时间差，全部是 5 ms；`0x84` 有 1583 个，全部是 5 ms。
`0x84` 原生四元数范数约 0.999946–0.999955，符合 int16 量化后的单位四元数。
`0xA4` 同样没有观察到失同步、无效时间戳或无效四元数，为后续研究短时姿态预测提供了适合的字段组合。
这些是静态采集与时序验证，本轮没有重新做用户转动、安装轴或动态精度验收。

**长报文异常：** `0xE1`（时间戳＋默认三组量）按协议应为每帧 28 字节，8 帧共 224 字节，
实际通知却持续为 200 字节，并出现残帧、失同步和不可能的时间戳。
该组初版实验解析器产生的帧率／角度变化统计不可靠，已从结论中排除并在 JSON 中标记。
更长的 `0x6F` 在 200 Hz 下未能完成配置回读，测试停止，`0xEF` 未执行。
没有把扩大 payload 当成可用提速方案，也没有假定截断发生在固件、模块缓冲还是系统栈的具体哪一层。

## 主动读取对照

所有请求均为已知 `FF AA 27 ...` 读寄存器指令，没有写配置、校准或保存。
请求线程与通知接收线程独立；测试窗口 8 秒，先预热 2 秒。并行窗口最多 4，避免堆积读取历史请求。

| 连续流与读取方式 | 寄存器响应率 | 含完整姿态的通知率 |
|---|---:|---:|
| 10 Hz 流＋角度单请求，目标 50 Hz，有写入确认 | 15.54 Hz | 19.75 Hz |
| 10 Hz 流＋角度并行读取，目标 100 Hz，无写入确认 | 16.35 Hz | 19.63 Hz |
| 20 Hz 流＋角度并行读取，目标 100 Hz，无写入确认 | 16.36 Hz | 23.38 Hz |
| 10 Hz 流＋四元数并行读取，目标 100 Hz，无写入确认 | 16.35 Hz | 20.25 Hz |
| 200 Hz 时间戳角度流＋回传率寄存器读取，目标 100 Hz | 16.48 Hz | 24.88 Hz |
| 200 Hz 时间戳角度流＋四元数读取，目标 100 Hz | 16.16 Hz | 24.88 Hz |

部分并行测试各出现一次读取超时，没有写入错误。主动读取没有使连续流提前交付，部分回复与流数据合并到同一通知。
这些结果只覆盖本轮的两个写入方式和有限窗口，不能当作全部固件／请求方式的绝对上限。

## USB 与 BLE 同帧接收时间差

以 `0x84` 时间戳＋四元数模式同时读取 USB 和 BLE，按完整 18 字节帧匹配，1592 帧全部找到 USB 对应帧：

| 比较对象 | 中位数 | P95 | 最大值 |
|---|---:|---:|---:|
| 每批全部 8 帧：BLE 接收时间减 USB 接收时间 | 31.71 ms | 56.33 ms | 88.50 ms |
| 每批最新一帧：BLE 接收时间减 USB 接收时间 | **13.72 ms** | **27.32 ms** | **55.45 ms** |

最小差值为 −2.05 ms，原样保留：USB 本身也有驱动和主机读取延迟，不能把它视作零延迟真值。
两种程序使用同一主机墙钟，BLE 用一次墙钟锚点加单调时钟差值，USB 在串口读取后取墙钟；这是近似的接收时间差。
没有测量传感器融合延迟、运动到声音的总延迟或绝对空口延迟，也没有校准设备 RTC。
结果支持继续只取每批最新姿态；把批内旧样本延后逐帧播放会增加历史数据的等待。

## 下一步选择

1. **真实无线交付频率：优先向厂商确认关闭打包／调整打包周期的固件或公开配置。** 需要的是更频繁的新通知，
   单改 RRATE 或把同一批拆成更多 OSC 包无法达到这一点。现有 macOS CoreBluetooth 中央端公开头文件没有连接间隔、
   通知 MTU 的设置入口，btleplug 也没有对应控制；已知 Windows 连接偏好测试结果见前一份报告。
2. **软件可继续研究：原生四元数＋角速度＋设备时间戳（`0xA4`）的时间对齐与短时预测。**
   本轮已确认该格式可读取；预测效果、动态误差和可感知延迟尚未实测，也未加入正式桥接管线。
   预测不增加实际 BLE 测量频率，若后续实现，必须与实测样本区别标记。
3. **需要接近 200 Hz 的真实交付时，继续使用已验证的 USB。** 评估其他无线设备时，应要求供应商提供实际通知周期、
   每通知样本数和端到端延迟，不能仅凭“200 Hz 采样”选型。未验证专用接收器能否改变这台传感器的打包行为。

可给厂商的具体问题（本轮未发送）：

> BWT901BLECL5.0，设备版本号 13115，回传率 200 Hz。在 macOS 和 Windows 上，默认格式每通知 160 字节、8 帧，
> 约 25 次通知/秒；换成只输出角度或四元数仍是 8 帧/通知。是否有公开寄存器或官方固件可以关闭打包，
> 或把约 40 ms 的打包周期缩短到 5–10 ms？是否支持外围设备发起更低延迟的连接参数请求？
> 新版协议的 `0xE1` 报文在这台设备上出现持续 200 字节通知和残帧，请提供该版本对应的长度限制、寄存器表和固件变更说明。

## 实验工具、恢复与范围

新增 [ble_probe.rs](../../crates/posebridge-cli/examples/ble_probe.rs)，复用已有 Cargo workspace 和依赖缓存：

```sh
cargo build --release --locked --example ble_probe
target/release/examples/ble_probe --device "scan 返回的平台标识" --seconds 8 --warmup 2
target/release/examples/ble_probe --device "平台标识" --seconds 8 --register 0x3d --poll-hz 100 --window 4 --write-mode command
```

工具本身不修改设备配置，只可选读取白名单内寄存器。支持新协议可变长度统计、原始通知记录、时间戳检查和四元数范数检查。
它是实验诊断工具，不发送 OSC。该轮实验时正式 `bridge`／C ABI 尚未接入新格式；
后续 PoseBridge 0.2 已补齐 `0x81/0x84/0xA4` 及 OSC v2，见[时间戳链路验证](2026-09-19-timestamp-pipeline.md)。
本轮外部实验脚本临时修改了 RRATE `0x03` 和输出格式 `0x0E`，每段都在 finally 恢复；没有 SAVE、校准、滤波或未知寄存器写入。
退出 BLE 后部分首次回读超时，稍后重试成功；长报文异常已单独记录，没有把失败读回当作验证成功。

最终回读 `0x03=0x0006`（10 Hz）、`0x0E=0x0061`，连同带宽、算法、滤波和版本寄存器，全部与实验前一致。
macOS Release 的 15 项原测试＋1 项实验格式测试，以及 fmt／Clippy 通过。本轮没有重新测 Windows 硬件或音频链路。

[结果 JSON](2026-09-19-ble-exploration.json) 保留测量统计、异常标记、恢复结果和原始日志哈希。
原始通知日志留在本机 `target/benchmarks/ble-exploration/`，未把整套厂商资料或 SDK 放入仓库。
